# US-006: Migrate ESP32 Platform To ESP-IDF 6.1.1

## User Story
As the robot platform maintainer, I want ESP-IDF 6.1.1 to be the sole supported
ESP32 SDK so the gateway firmware builds and runs against one current,
reproducible toolchain without changing transport contracts or moving control
authority away from the Pico.

## Current And Target Behavior

### Current

- The ESP32 repository records ESP-IDF 5.5 in `sdkconfig`, the shared
  toolchain requirements, and `tools/robot_adapter.py`.
- The adapter checks `IDF_PATH` and then a hard-coded
  `/home/behzad/Projects/esp-idf` fallback; it neither follows the installation
  selected by EIM nor rejects an unsupported ESP-IDF version.
- Component declarations mix legacy aggregate driver dependencies with some
  ESP-IDF 5/6 split driver components. The lock file uses the existing format
  and identity.
- The current firmware implements Pico UART log forwarding, multi-client
  WebSocket telemetry, Wi-Fi, Bluepad32 controller connectivity, and controller
  snapshot forwarding with a heartbeat no slower than 100 ms.
- ESP-IDF 6.1.1 is already selected in EIM, while a legacy 5.5 checkout,
  environments, constraints file, and registry residue may still exist.

### Target

- ESP-IDF 6.1.1 is the only supported and documented SDK version for the
  classic `esp32` target.
- Project-owned components declare each ESP-IDF 6 split component they consume
  directly, starting with `esp_driver_uart`; additional migration errors are
  resolved by the same direct-dependency rule rather than compatibility shims.
- `sdkconfig` and `dependencies.lock` are regenerated by 6.1.1 while preserving
  the intended target, Bluetooth controller-only mode, Bluepad32 custom
  platform, Wi-Fi/WebSocket support, UART assignments, partition layout,
  logging, and timing behavior. The ESP-IDF 6 lwIP minimum is accepted only
  after device behavior passes.
- The adapter selects `IDF_PATH` when explicitly set; otherwise it reads the
  selected, finished installation from `~/.espressif/tools/eim_idf.json`. It
  reports the activated SDK's actual version and accepts exactly 6.1.1.
- The 5.5 installation is removed only after host and device verification
  passes, a fresh legacy audit finds no unique material, the registry is backed
  up, and the owner explicitly approves deletion outside the workspace.

## Boundaries And Non-Goals

- ESP32 continues to own Wi-Fi/WebSocket services, Pico log forwarding,
  Bluetooth controller connectivity and normalization, controller snapshot
  transport, diagnostics, and platform support.
- Pico continues to own command admission, freshness, stale-input behavior,
  stop/recover semantics, motor output, encoders, timing-sensitive control, and
  final safety authority.
- Android continues to own operator UI, app state, and client transport
  lifecycle.
- Command, telemetry, controller snapshot, heartbeat, wiring, UART assignment,
  and subsystem ownership interfaces do not change.
- Dual-version compatibility, ESP-IDF 5.5 fallback behavior, target migration
  away from classic `esp32`, dependency upgrades unrelated to ESP-IDF 6.1.1,
  protocol redesign, wiring changes, and powered traction or motion testing are
  out of scope.
- EIM `core` and `ide` remain installed. `test-specific`, `ci`, `docs`, and the
  local `mcp` feature remain disabled.

## Acceptance Criteria

- **AC-001:** A clean configuration and build from an empty build directory
  completes under the activated ESP-IDF 6.1.1 installation without a
  project-owned missing-component error or obsolete project Kconfig value.
- **AC-002:** BTstack, controller transport, and any other affected component
  name the ESP-IDF 6 split components they directly consume, beginning with
  `esp_driver_uart`, without adding a 5.5 compatibility path.
- **AC-003:** The regenerated `sdkconfig` identifies ESP-IDF 6.1.1 and classic
  `esp32` and preserves Bluetooth controller-only mode, the Bluepad32 custom
  platform, Wi-Fi/WebSocket support, UART assignments, partition layout,
  logging, and timing settings.
- **AC-004:** The regenerated `dependencies.lock` uses the ESP-IDF 6 lock
  format and records the ESP-IDF 6.1.1 identity for target `esp32`.
- **AC-005:** Adapter tests prove `IDF_PATH` precedence, selected EIM
  installation discovery, a clear missing-installation result, and rejection
  of every activated version other than exactly 6.1.1; doctor output reports
  the actual activated version rather than a configured constant.
- **AC-006:** ESP32-local and shared toolchain documentation declare 6.1.1 as
  the sole baseline, and review finds no change to command, telemetry,
  controller snapshot, heartbeat, UART, wiring, or subsystem ownership
  contracts.
- **AC-007:** Before any flash, execution pauses until the exact ESP32 serial
  device is connected and confirmed and the owner grants Gate 1 approval. The
  flash and all device checks run on a power-isolated bench with traction/motor
  power physically disabled.
- **AC-008:** Retained device observations show repeated boots with expected
  serial logging and successful Wi-Fi connection, loss, and recovery using the
  ESP-IDF 6.1.1 firmware.
- **AC-009:** Retained integration observations show simultaneous WebSocket
  telemetry to two clients and Pico UART log forwarding without changing the
  existing telemetry contract.
- **AC-010:** Retained integration observations show Bluetooth controller
  pairing and reconnection plus controller snapshot forwarding, including the
  unchanged repeated-state heartbeat cadence.
- **AC-011:** Any failed or inconclusive device or integration check leaves the
  migration incomplete and preserves every ESP-IDF 5.5 installation artifact;
  build success alone cannot satisfy or bypass the device criteria.
- **AC-012:** Immediately before cleanup, a fresh audit confirms that
  `/home/behzad/Projects/esp-idf` contains no unique material: its untracked
  BTstack matches the vendored project copy and `hello_world` matches the
  upstream example. Any unique or unexplained material aborts cleanup.
- **AC-013:** After all prior criteria pass and the owner explicitly approves
  the exact outside-workspace deletion list, the EIM registry is backed up into
  the ignored parent `temp/` area and only the audited 5.5 checkout, both 5.5
  Python environments, the 5.5 constraints file, and stale 5.5 registry entries
  are removed.
- **AC-014:** With 6.1.1 activated, `idf_tools.py uninstall --dry-run` output is
  retained and reviewed before removing only tool versions and archives that
  6.1.1 does not use.
- **AC-015:** Post-cleanup checks show EIM still selects an activatable 6.1.1,
  no project or inspected shell configuration references 5.5, adapter doctor
  passes, and a second clean build from an empty build directory passes.

## Dependencies And Assumptions

- US-002 informs exact board identity, connected-device facts, and power
  isolation; it does not block host migration work. The exact board remains
  unverified until physical evidence closes `Q-US002-004`.
- US-003 informs adapter result contracts, Gate 1 behavior, scenario naming,
  and evidence promotion; it does not transfer ESP-IDF ownership away from the
  ESP32 repository.
- The observed EIM registry is format version 3.0 and currently selects a
  finished installation named `v6.1.1`. The adapter must treat malformed,
  missing, unselected, unfinished, or non-6.1.1 entries as explicit failures.
- The new lwIP minimum is acceptable only if AC-008 through AC-010 pass; no
  source-level assumption substitutes for those observations.
- Cleanup paths and contents are execution-time facts. The implementation plan
  must resolve and validate an exact manifest before requesting destructive
  approval; this story does not pre-authorize deletion.

## Unknowns And Decisions

- **Decided:** Use exact-version selection, not a compatible range: 6.1.1 is
  the sole supported baseline.
- **Decided:** Use explicit direct component dependencies for ESP-IDF 6 split
  drivers; do not hide missing declarations through transitive dependencies.
- **Decided:** Preserve the current runtime interfaces and the ESP32
  gateway/transport-only boundary.
- **Decided:** Device verification gates legacy cleanup, and any failed or
  inconclusive device result retains 5.5 and leaves the story open.
- **Decided:** No motor-power or motion test is permitted. If verification
  unexpectedly requires one, stop and refine separate safety-control work.
- **Open until execution:** Exact serial device identity, fresh device
  availability, the legacy deletion manifest, and whether the cleanup audit
  discovers unique material.

## Learning To Retain

Document the ESP-IDF 6 direct-dependency rule and the difference between a
configured SDK version and the version actually activated by EIM. These are
toolchain-maintenance lessons; no new control, electrical, or motion concept is
introduced by this story.
